# Архитектура

## Стек

| Область | Выбор | Почему |
|---|---|---|
| Язык | Swift 6 (строгая конкурентность) | Нативный доступ ко всем API окон и системы macOS |
| Сборка | Swift Package Manager | Работает без Xcode, проект — обычные текстовые файлы |
| Оболочка | AppKit | Прозрачные окна, уровни окон, глобальные события мыши — SwiftUI этого не даёт |
| Рендер | SpriteKit | Спрайтовая анимация, физика для мячика, встроен в систему |
| Интерфейс (настройки, статус) | SwiftUI | Быстро делать обычные формы и поповеры |
| Тесты | Swift Testing | Идёт с тулчейном |
| Форматирование | `swift format` | Идёт с тулчейном |
| Хранение | JSON-файл в `~/Library/Application Support/DesktopPet/` | Одно маленькое состояние, база данных не нужна |
| Графика | Пиксель-арт, PNG спрайт-листы + JSON-манифест анимаций | Простой пайплайн из Aseprite/Piskel |
| Минимальная система | macOS 15, Apple Silicon | Проект для себя |

Сторонних зависимостей нет и добавлять их стоит только при явной необходимости.

### PetCore — ядро

Чистый Swift, **не импортирует AppKit и SpriteKit**. Ничего не знает про окна, пиксели и системные часы.

- На вход: прошедшее время (`advance(by:)`) и события мира (`WorldEvent`: курсор рядом, погладили,
  покормили, пользователь ушёл/вернулся).
- На выход: команды (`PetCommand`: идти в точку, проиграть анимацию, достать мячик).
- Время и случайность передаются снаружи (часы и генератор — параметры), поэтому любое поведение
  воспроизводимо в тесте: «прошло 6 часов без еды → питомец голоден и просит есть».

Это главное архитектурное правило проекта: **вся логика — в ядре, под тестами; оболочка только
показывает и передаёт события.**

### DesktopPet — оболочка

- **Overlay** — прозрачное окно без рамки поверх всех приложений на каждом экране.
- **Scene** — SpriteKit-сцена: узел питомца, предметы (мячик, еда), пол.
- **Sensors** — источники событий: положение курсора, простой пользователя, активное приложение.
- **UI** — значок в меню-баре, поповер статуса, окно настроек.
- **PetController** — единственное место, где ядро встречается с миром.

## Ключевые решения

### 1. Один прозрачный оверлей на экран, а не маленькое окно вокруг питомца

Питомцу нужны бег по всему экрану, мячик с физикой и предметы — это одна общая сцена.
Окно пропускает клики насквозь (`ignoresMouseEvents = true`) и «ловит» мышь, только когда курсор
над питомцем или предметом (следим за глобальной позицией курсора).

Альтернатива — маленькое окно, которое ездит за питомцем: проще и дешевле, но каждый предмет
становится отдельным окном и физика между ними усложняется.

**Риск:** полноэкранная прозрачная сцена может заметно грузить GPU/батарею.
**Проверка:** спайк в начале M1 с замером в Activity Monitor. Меры — снижать FPS в покое, ставить
сцену на паузу, когда питомец спит или скрыт. Если не поможет — откат на маленькое окно.

### 2. Поведение: потребности → «мозг» на полезностях → занятия-сценарии

- **Needs** убывают непрерывно.
- **Brain** раз в несколько секунд (или когда занятие закончилось) оценивает кандидатов:
  у каждого занятия есть вес, зависящий от потребностей, времени суток и недавних событий, плюс
  доля случайности. Выигрывает занятие с лучшей оценкой.
- **Activity** — конечный автомат из шагов («подойти к мячу → толкнуть → бежать за ним → …»),
  который можно прервать событием с более высоким приоритетом (взяли на руки, погладили).

Так новое поведение добавляется как ещё одно занятие, без переписывания общего автомата.

Характер Сенеки (спокойный мудрец с редкими срывами в охоту) задаётся не кодом, а **параметрами
темперамента** — весами занятий и порогами в мозге. Это отдельная структура данных в ядре:
её можно балансировать, не трогая логику, и подменить для другого персонажа.

### 3. Симуляция по дельте времени, включая офлайн

При запуске ядро получает «прошло N часов с последнего сохранения» и прогоняет потребности вперёд.
Офлайн-убывание ограничено сверху, чтобы после отпуска не найти питомца в безнадёжном состоянии.

### 4. Анимации — данные, а не код

Каждое состояние (`idle`, `walk`, `sleep`, `eat`…) описано в манифесте: файл спрайт-листа, кадры,
длительности, зацикленность. Ядро называет анимацию по имени, сцена её проигрывает.
Замена графики или добавление скина не требует правок кода.

Мейн-кун длинный и с большим хвостом, поэтому кадр широкий (предварительно 64×48). Отсюда два
требования к сцене: точка опоры спрайта — под лапами, а не в центре кадра, и попадание мыши
проверяется по силуэту, а не по прямоугольнику.

### 5. Без Xcode, пока он не понадобится

Сборка, тесты и запуск идут через `make`. Ресурсы — обычные PNG через ресурсы SwiftPM
(без asset-каталогов, которым нужен Xcode). Собрать `.app`-бандл можно скриптом.
Xcode пригодится позже — для Instruments и отладчика.

Известная особенность: без Xcode `swift test` не находит макро-плагин Swift Testing, поэтому в
`Makefile` путь к нему передаётся явно. Запускать тесты через `make test`.

### 6. Разрешения системы

MVP не должен просить ничего страшного:

- позиция курсора и глобальные события мыши — без разрешений;
- простой пользователя (`CGEventSource.secondsSinceLastEventType`) — без разрешений;
- активное приложение (`NSWorkspace`) — без разрешений;
- содержимое нажатий клавиш — **не читаем** (нужен был бы Accessibility/Input Monitoring).

Границы чужих окон (для хождения по окнам, после MVP) доступны через `CGWindowList` без записи экрана.

### 7. Распространение

Для себя — `make run` или локальный `.app`. Другу — zip с `.app`, подписанным ad-hoc; при первом
запуске нужно снять карантин (`xattr -dr com.apple.quarantine DesktopPet.app`).
